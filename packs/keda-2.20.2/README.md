# KEDA

![Version: 2.20.2](https://img.shields.io/badge/Version-2.20.2-informational?style=flat-square)

[KEDA](https://keda.sh) (Kubernetes-based Event Driven Autoscaler) is a CNCF graduated project that enables fine-grained autoscaling for event-driven Kubernetes workloads. KEDA can drive the scaling of any container in Kubernetes based on the count of events needing to be processed, including scale to and from zero.

KEDA deploys three components:
- **KEDA Operator** - Manages ScaledObjects, ScaledJobs, and TriggerAuthentications
- **KEDA Metrics API Server** - Serves external metrics API for Kubernetes HPA
- **KEDA Admission Webhooks** - Validates and mutates KEDA custom resources

## Prerequisites

- Kubernetes >= v1.29.0
- Helm >= 3.x

## Upgrade

To upgrade KEDA within the pack, update the chart version in `pack.json` and download the new chart:

```bash
# Download the new chart version
helm pull kedacore/keda --version <new-version> --destination charts/
```

Update `pack.json` with the new version and chart filename. Update the `values.yaml` `pack.content.images` to reflect the new image tags. Ensure the `values.yaml` chart section is synced with the new chart's defaults.

> [!CAUTION]
> Review the [KEDA changelog](https://github.com/kedacore/keda/releases) for breaking changes before upgrading. Pay special attention to CRD changes that may require manual intervention.

## Usage

### Installation

KEDA is installed automatically when the pack is added to a cluster profile. The default configuration deploys all three components (operator, metrics server, admission webhooks) with secure defaults.

### Creating a ScaledObject

After installation, create a `ScaledObject` to autoscale your workload:

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: my-app-scaler
  namespace: default
spec:
  scaleTargetRef:
    name: my-app
  minReplicaCount: 0
  maxReplicaCount: 10
  triggers:
    - type: cron
      metadata:
        timezone: America/New_York
        start: 0 * * * *
        end: 30 * * * *
        desiredReplicas: "3"
```

### Using TriggerAuthentication

For sensitive scaler configurations, use a `TriggerAuthentication` resource:

```yaml
apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication
metadata:
  name: my-trigger-auth
  namespace: default
spec:
  podIdentity:
    provider: aws-eks
```

### Validating the Installation

#### Health Check

Verify the KEDA components are running and registered correctly:

```powershell
# Check all KEDA pods are running
kubectl get pods -n keda

# Verify the KEDA CRDs are installed
kubectl get crd | Select-String keda.sh

# Verify the external metrics API is registered
kubectl get apiservice v1beta1.external.metrics.k8s.io
```

Expected results:
- 3 pods running in the `keda` namespace (operator, metrics server, webhooks)
- 6 `keda.sh` CRDs installed
- The `external.metrics.k8s.io` API is `Available=True`

#### Scaling Test

Run the following steps to verify autoscaling works correctly:

```bash
# 1. Create a test namespace
kubectl create namespace keda-test

# 2. Apply a test Deployment
kubectl apply -n keda-test -f echo-server.yaml

# 3. Apply a ScaledObject (creates an HPA automatically)
kubectl apply -n keda-test -f scaledobject.yaml

# 4. Verify scaling works
kubectl get pods -n keda-test
kubectl get scaledobject -n keda-test
kubectl get hpa -n keda-test

# 5. Cleanup when finished
kubectl delete namespace keda-test
```

> [!NOTE]
> The `scaledobject.yaml` in this example uses a `cron` trigger. The pods will scale to the desired replicas during the defined cron window and back to the minimum (0) outside of it.
